# Чек-лист регистрации на сайте Lamoda

> **Чек-лист - это документ, содержащий список проверок. Он менее подробен по содержанию, в нем отсутствуют шаги, как в тест кейсе. Один пункт чек листа описывает одно направление для проверки.**

Чек-лист содержит:
- список проверок с требуемой степенью детализации
- статус проверок (результат)
- сборка, на которой проводилось тестирование
- тестовое окружение (если применимо)
- кто проводил тестирование

**Объект тестирования**<br/>
Сайт: lamoda.ru<br/>
Раздел: Регистрация пользователя<br/>
Окружение: Desktop, Windows 10 / Google Chrome

**Цель тестирования**<br/>
Проверить корректность работы всех способов регистрации:
- Регистрация по номеру телефона
- Регистрация по Email
- Регистрация через соцсети
- Проверка документации и UI-элементов

*Почему для этого проекта я выбрал чек-лист, а не тест-кейсы?*<br/>
- скорость составления - чек-лист можно написать быстрее и сразу приступить к тестированию
- гибкость - чек-лист оставляет пространство для исследовательского тестирования, не загоняя в жесткие рамки последовательных шагов
- обзорность - глядя на чек-лист, легко оценить общее покрытие функционала (но не забываем про матрицу трассируемости)
- удобство для регресса - по чек-листу удобно быстро пройтись при повторном тестировании

> При этом позже, если потребуется, самые важные или сложные проверки я могу расписать в виде подробных тест-кейсов.

Что я знаю точно:
- есть форма регистрации с полями
- есть разные способы регистрации

Чего я НЕ знаю (и это нужно выяснять или предполагать):
- какие требования к длине пароля
- какие символы допускаются в email
- есть ли ограничения на формат номера телефона
- как система ведет себя при повторной регистрации того же пользователя
- какие сообщения об ошибках должны показываться

В таких случаях я опираюсь на:
- общепринятые практики (например, email должен содержать "@" и домен)
- логику (если пользователь уже есть - сообщить об этом)
- аналогии с другими формами на этом же сайте

## Далее расписаны, примененные, техники тест-дизайна:
### Классы эквивалентности<br/>
Эта техника помогает не проверять все возможные значения, а разбить их на группы (классы), внутри которых поведение системы будет одинаковым.<br/>
**Для поля "Email" я выделил такие классы:**

| Класс эквивалентности | Пример | Почему это отдельный класс |
| --- | --- | --- |
| Валидный email | user@mail.ru | Должен приниматься |
| Email без @ | usermail.ru | Типичная ошибка пользователя |
| Email с пробелами | user @mail.ru | Проверка обработки пробелов |
| Пустое поле | - | Проверка обязательности поля | 

**Для поля "Пароль" классы эквивалентности:**

| Класс эквивалентности | Пример | Почему это отдельный класс |
| --- | --- | --- |
| Только буквы | password | Должен приниматься (если есть требования к сложности - могут быть нюансы) |
| Только цифры | 12345678 | Должен приниматься или выдавать ошибку (зависит от требований) |
| Буквы + цифры | pass1234 | Базовый валидный пароль |
| Со спецсимволами | pass@123 | Проверка поддержки спецсимволов |
| Пустое поле | - | Проверка обязательности поля | 

### Анализ граничных значений

Эта техника применяется, когда есть числовые диапазоны или ограничения длины.<br/>
Предположим, что требование к паролю: минимум 8 символов.<br/>
Тогда граничные значения:
- 1 символ (значительно ниже границы) - должна быть ошибка
- 7 символов (граница - 1) - должна быть ошибка
- 8 символов (граница) - должен приниматься
- 9 символов (граница + 1) - должен приниматься
> Именно поэтому в чек-листе есть пункты "ввод 1-го символа", "ввод 7 символов", "ввод 8 символов".

### Таблица принятия решений

Для регистрации через соцсети логика простая, но ее можно представить в виде таблицы:

| Условие | Аккаунт существует | Действие пользователя | Ожидаемый результат | 
| --- | --- | --- | --- |
| Сценарий 1 | Да | Нажимает "Войти через VK ID" | Успешная авторизация, привязка аккаунта |
| Сценарий 2 | Нет | Нажимает "Войти через VK ID"| Предложение создать новый аккаунт или сообщение об ошибке |

Покрыто в чек-листе двумя проверками для каждой соцсети.

Отдельное внимание я уделил **негативным сценариям** - тому, как система реагирует на ошибки пользователя.<br/>
В чек-листе это:
- ввод несуществующего номера
- пустые поля
- ввод букв в поле для цифр
- ввод спецсимволов
- повторный ввод неправильного пароля
> Это необходимо, так как пользователи всегда будут ошибаться, и система должна подсказывать им, что не так, а не просто "падать" или ничего не делать.
